- [x] **Phase 5 — QA, performance, deploy-readiness**:
  - **Visual QA tooling**: installed Playwright + Chromium (`npx playwright install chromium`). `scripts/qa-screenshots.mjs` opens the dev server (starting one itself if nothing's listening), captures both home and `/book` at 390×844 and 1440×900, and — crucially — forces `prefers-reduced-motion: reduce` via Playwright so the camera *snaps* straight to each stage's exact authored position instead of easing toward it. Without that, headless Chromium throttles `requestAnimationFrame` in a backgrounded tab, which left the damped camera short of its target within any reasonable wait — a tooling artefact, not a real bug for actual focused-tab users, but it made screenshots meaningless until forced. Headless WebGL rendering worked using `--use-gl=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`; did not need to fall back to overlay-only testing. Screenshots saved to `qa-screenshots/` (gitignored).
  - **Real problems found and fixed** by actually looking at the screenshots:
    - **Wheels stage (3) camera was far too close** — the front wheel filled almost the entire frame and Bloom blew the whole image out to a wash of solid cyan, to the point the active stage-indicator dot disappeared into the glare. Pulled the camera back in `cameraPath.ts` (~1.25 units from the wheel → ~3.9).
    - **Engine stage (4) camera was nearly touching the car's own front bumper** (0.25 units of clearance), so the frame was dominated by the car's own translucent shell rather than a clear "rising over the bonnet" view. Pulled it back to ~1.1 units of clearance.
    - **Aspect-ratio FOV bug**: `fov` on a `PerspectiveCamera` is *vertical*; on a narrow/portrait phone screen the *horizontal* FOV for the same vertical fov is much smaller than on a landscape screen. Wide shots tuned looking at a landscape viewport (the diagnostics side-view, the arrival establishing shot) didn't fit at all on mobile — confirmed by comparing identical stages side-by-side on both viewports. Fixed by widening the vertical fov adaptively in `CameraRig.tsx` when aspect < 1, keeping landscape/desktop (already correct) untouched.
    - **Stage-indicator dots washed out** against bright/bloomed parts of the scene (same root cause as the wheels issue, visible even after fixing the distance). Gave the dot stack a subtle dark backdrop pill in `StageOverlay.tsx`.
  - **Checked and found fine**: CTA-button/caption spacing during stage 6 (both viewports), `/book` page layout at both widths (services grid correctly collapses to one column on mobile, form fully labelled and tappable), the themed 404 page, the WebGL fallback screen.
  - **Minor, left as-is** (out of scope for this phase): dust particles render as small squares, not soft round motes — that's three.js's default point-sprite shape with no texture (and this project has a "no assets" rule); a circular look would need a small custom shader, which is a Phase-4-style visual-polish item, not a QA bug. The Next.js dev-mode "N" badge appears in several screenshots — that's dev-tooling chrome, absent from production builds, not an app issue.
  - **Bundle size** (`.next/diagnostics/route-bundle-stats.json` — Next 16's Turbopack build no longer prints the classic First Load JS table, so this is where the real numbers live): `/` 456.0 KB, `/book` 467.4 KB, `/_not-found` 451.7 KB, all uncompressed JS.
  - **Lazy-loading three.js**: confirmed (and had to properly fix, not just confirm) that neither `/book` nor the WebGL-fallback path ever downloads the ~1.1 MB three.js/@react-three/fiber/drei/postprocessing bundle. This needed a restructure: introduced `SceneGate.tsx`, loaded from `HomeClient.tsx` via `dynamic(() => import("./SceneGate"), { ssr: false })`. SceneGate does a synchronous `hasWebGL()` check via a lazy `useState` initializer — safe *specifically* because SceneGate itself never server-renders (nothing to hydration-mismatch against), unlike an earlier attempt using `useEffect` + `setState`, which the project's `react-hooks/set-state-in-effect` lint rule correctly rejected, and which also wouldn't have worked anyway (more below). Found one real bug while building this: SceneGate must *not* statically `import Experience` — doing so packs three.js into SceneGate's own chunk, so it downloads as soon as SceneGate's chunk loads, before the WebGL check ever runs. `Experience` has to stay behind its *own*, separate `dynamic(ssr:false)` import, with its *rendering* (not just its declaration) gated behind the check. Wrote `scripts/qa-fallback-check.mjs` to verify this with a real browser (simulates no WebGL, confirms the fallback renders and no three.js chunk is requested) — it caught this exact bug before I could report it as "done" incorrectly.
  - **Per-frame allocation / leaked-listener audit**: read through every scene file (`CameraRig`, `HologramPart`, `HologramShell`, `HologramCar`, `BrakeAssembly`, `EngineBlock`, `Diagnostics`, `Markers`, `Atmospherics`) plus `ScrollRig`, `StageOverlay`, `ConversionOverlay`. Found nothing to fix — every per-frame mutation goes through a persistent ref or typed array (no `new Vector3()`/`new Color()`/`.slice()`/array-recreation inside any `useFrame`), and swept the whole `src/` tree for every `addEventListener`/`gsap.ticker.add`/`ScrollTrigger.create`/`new Lenis` to confirm each has a matching, correctly-scoped cleanup (`removeEventListener`/`gsap.ticker.remove`/`.kill()`/`.destroy()`) — all four do, all inside the right `useEffect` cleanup function.

Code review separately confirms wheel/brake spin freezes, the diagnostics scan-plane sweep hides, dust drift freezes, and all label/caption fades hard-cut instead of ramping — all previously built in 3B/3C, just now actually exercised and screenshotted rather than only reasoned about.
